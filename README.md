# blockporter

直接改 Minecraft Java 版存档（`.mca`）的命令行工具。不依赖 Amulet，也不用启动游戏。用来把旧版本里玩家改过的方块搬进新版本的空板，再把搬完之后对不上的方块、索引和残块清掉。

项目分两块：

| | 是什么 | 编出来是什么 |
|---|---|---|
| **nbtrw** | 读写 NBT、区块、区域文件、整个存档的库 | `libnbtrw.so`，以及一个只读 demo `nbtrw` |
| **blockporter** | 搬图和修图 | `merge`、`fixer`、规则插件 `rules.so.<版本>` |

规则插件一个版本一份：**`rules.so.26.1.1`（Java Edition 26.1.1，DataVersion 4788）** 和 **`rules.so.26.3`（26.3，DataVersion 5023）**。`fixer` 要求存档（`level.dat`）的 DataVersion 和插件完全一致，否则拒绝动手；存档里没升级的老区块（区块自己的 DataVersion 不一样）规则不判。

>

## 和上一版的差别

“上一版”是发布仓库里 2026-10-25 的那一版（规则插件 ABI NBR4）。

照旧文档跑会出错的（2026-11-14 下半这一轮改的在最前面）：

- **去掉了 `chunkunit` 参数**。merge 少一个参数：`./merge <new> <now> <old[,old...]> <x1> <y1> <z1> <x2> <y2> <z2> [dims]`；
  fixer：`./fixer <path> <x1> <y1> <z1> <x2> <y2> <z2> [dims] [rules]`。现在每种操作都按自己的最小单位、向外取整到那个单位，范围外只读不写：
  搬方块、判物理、单条计划刻/POI/实体记录严格按给定的 x/y/z；删区块、删光照/高度图、整理区块（Y、重复段、调色板）按 x/z 碰到的区块整块做，**不看 y**；
  整理区域文件按碰到的区域文件做。所以以前“整块在范围内才删”的空区块/`InhabitedTime` 是 0 的区块，现在只要 x/z 碰到就删。
- **fixer 的规则插件由最后一个参数给**（`rules.so.26.1.1`、`rules.so.26.3`…），不给就用当前目录的 `./rules.so`；不再找程序旁边的。
  `make` 不再链 `rules.so`，要用默认的就自己 `ln -sf rules.so.26.1.1 rules.so`。规则源码改名 `rules.cpp.<版本>`，`make rules` 每个版本编出一个 `rules.so.<版本>`。

- **编译**：`make` 现在编全部（库、demo、merge、fixer、规则插件）；`make nbtrw` 只编库和 demo，`make blockporter` 只编 merge/fixer/插件；清理从 `make clean` 改名 **`make clear`**。另外要装 lz4、xxhash 的开发包（见下面“编译”）。
- **规则插件 ABI 升到 NBR7**（`0x4e425237`），旧的 `rules.so` 要按新 `rules.hpp` 重编，fixer 会拒绝装旧插件。接口里去掉了插件内部的东西（支撑档、形状、支持集都放进插件自己的 `priv`），以后改 rules.cpp 不用再动 ABI；主机把方块名字/属性按存档格式取好交给插件，插件交回要写的方块和要补的计划刻。
- **merge 跨版本照搬**：`now`、`new`、`old` 的 DataVersion 不同照样合，方向不限（高版本合进低版本、有 mod 的合进没 mod 的都不拦）；方块按 `new` 那块的格式写，但名字不改（见下面“merge”）；实体/POI 按 `new` 的版本写（1.17 以前的 `new` 实体写进区块里）。日志里不再有“区块版本不同”。
- **merge 搬 POI 改成按位置放**：`now` 的 POI 落在 `new` 已经有 POI 的同一格时，换掉 `new` 那条（以前是追加，重复留给 fixer）。`new` 那块 POI 形状坏时整块跳过，记坏POI。
- **merge 不补段**：`new` 里这一段 section 不在（或者没有 `block_states`）的格子跳过，记“缺段跳过”。以前要写方块时会补一段空气。
- **fixer 会删 `InhabitedTime` 缺失或不是数的区块**（整块在范围内时）：游戏读的时候当 0。以前是补写一个 0、不删。

这一轮（2026-11-14 下半）的其它变化：

- **merge/fixer 先走区域文件**：范围碰到的区域里没有 region 文件（或读不出来）的整个跳过；区域里只走表头上有的区块。范围可以随手给到整个世界边界。
- **表头偏移异常的格子照游戏当“没有”**（偏移指在表头里、扇区数是 0、偏移在文件外：游戏 WARN 一声当没有），fixer 整理文件时把它们清成 0，不再当坏块、也不再让整理失败。
- **坐标指到别的区块的方块实体、计划刻，fixer 迁到坐标所在的区块里**（游戏读档时方块实体会折回本区块落到一个不相干的格子上，计划刻直接丢掉）。
  目标区块没有就删掉这条，目标那一格已经有了就留原来的、删这条，读不出来就原样留着。没有坐标的、整个区块挪过位置跟着区块走的照旧改到本区块里。
- **整理区块（Y、重复段、调色板）挪到最后整理文件时做，整趟只做一遍**：在删完区块、删完空文件之后。
- **规则多重算五种外观**：蘑菇方块的面、音符盒的音色、滴水石锥（26.3 还有硫磺尖刺）的粗细、树叶的 `distance`、脚手架的 `distance`/`bottom`。
  `distance=7` 又不是 `persistent` 的树叶不拆，交给游戏慢慢腐烂。红石线的连接要看斜对角的格子，超出“只看六邻”，不做。
- **26.3 的规则插件**：方块表、形状、规则都在 26.3 的 jar 上对拍过；26.3 存档里没写的属性按默认值补全再判。

2026-11-21 复查修掉的：

- **fixer 删光照也严格按范围**：只删范围碰到的区块的光照/高度图，范围外紧挨着的邻居不再动（以前周围一圈 3×3 也删光照）。

- **fixer 迁移错位的方块实体时，不再把目标区块的位置先改掉**：目标区块自己的 xPos/zPos 也不对时，这条先留着（再跑一趟会迁过去）；
  以前会让目标区块里本该跟着它走的方块实体留在错的坐标上。
- **fixer 查重复 UUID 认得 Long_Array 写的 UUID**，merge/fixer 认得 `Pos` 用整数写的实体的位置（游戏都照读）。
- **merge 搬 POI 时 now 自己同一格有几条**，照游戏留一条（同类型留先来的）。
- **区域文件名只认游戏写的样子**：`r.01.0.mca`、`r.+1.0.mca` 这种游戏不读的文件不再当成区域，也不会让同一个区域被处理两遍。

这一轮（2026-11-14）全量检查修掉的：

- **merge 只碰范围里的区域文件**。以前区域范围算宽了 16 倍，范围外凡是有文件的区域都会被读一遍；其中有读不出来的，整趟还会报失败。
- **fixer 删“整块在范围内”的空区块时，不再被只有光照的段挡住**。1.17 及以前的区块上下各带一段只有光照的段，以前这种区块永远不算整块在范围内，全空气或 `InhabitedTime` 是 0 也删不掉。
- **表头坏了的区域文件**：偏移是 0、扇区数不是 0 的格子现在也当坏块删掉（以前清不掉，fixer 每次整理这个文件都报失败）；偏移指在表头里的格子，往里写区块时不会再把时间戳表覆盖掉。
- **坏 NBT 不再把程序拖死**：每层都谎报长度的嵌套列表，以前几十 KB 就要转一秒、再大能把内存吃光，现在读坏就停。
- 带 NaN 浮点数的方块实体，merge 不再把它所在的格子一律当成“改过”。
- 还没解决：NBT 嵌套几万层以上会爆栈崩溃（正常存档不会有，游戏自己最多读 512 层）。

存档格式：

- **区块压缩支持 lz4，外置的 `.mcc`（特别大的区块）也能读写**，和游戏的 `RegionFile` 互相读写对拍过。以前这两种都当“压缩类型不支持”跳过。模组的自定义压缩（类型 127）仍然读不了，只记日志、跳过。
- **库/merge/fixer 支持 26.3、26.4 的存档格式**，全按 DataVersion 判断：26.3 快照 7 起的新调色板写法（`id`/`properties`、字符串条目），26.4 快照 1 起的 `status` 字段名和每格一个的 biomes。以前在这些存档上 fixer 会把所有区块当成“没生成完”整块删掉。fixer 仍要求 `rules.so` 和存档的 DataVersion 完全相等，修新版本的存档要配对应版本的插件。
- **能读写 1.13（DataVersion 1451）以后各版本的区块**：一个存档里没升级的老区块按它自己的 DataVersion 读。段的方块状态照 26.1.1 载入老区块的样子读（游戏先升级再读：长度不对补齐/截断、调色板补空气……），拿原版 jar 逐格对拍过。1451 以前和没写 DataVersion 的区块 fixer 跳过不动。
- **新格式里 `data` 写成 Int 数组或数值列表的段，游戏照读**；以前会被当成坏段删掉，现在不动（merge 遇到这种区块跳过）。

fixer：

- **以游戏为准判坏**：游戏读档时会报错（ERROR/WARN）的按最小单位删，不报错的不动（下面“fixer”一节有细节）。和以前比：新加“修 NBT”一步（在规则之前）；段的 `Y` 不是 Byte 改成 Byte（以前删这一段），同一个 Y 有几段留最后一段（以前留最前面那段，游戏读的是最后那段）；`sections`/`block_states`/方块实体表类型不对，游戏当没有，不再整块删；POI 坏段只删那一段（以前整块重建），没有 `free_tickets` 的记录留着；实体区块 `Position` 坏了按文件位置重写（以前整块删），没有 `UUID`/`Pos` 的实体留着，乘客一个个判。
- **区块的 DataVersion 和规则插件不一样时，规则不判它**（存档里没升级的老区块，方块可能改过名）：不拆不改、计划刻不拿方块对、POI 不按方块补删；POI 文件的 DataVersion 不一样也不动（写回会改掉 DataVersion，游戏就不再升级它）。日志里记“版本和规则不同跳过”“版本不认识跳过”。
- **`sections` 形状坏（元素不是 compound）的邻居区块按“读不出来”处理**，不再当成全空气去拆旁边的方块。
- **流动水/流动岩浆的计划刻（`minecraft:flowing_water`/`flowing_lava`）不再被当成对不上删掉。** 计划刻和方块对不对得上现在由规则插件判断。
- **实体区块没有 `DataVersion` 不再当坏数据整块删**（游戏当它是 -1 照样读，中文 实体格式）；在但不是 Int 才算坏。

merge：

- **merge / fixer：维度列表按目录去重。** `overworld` 和 `minecraft:overworld` 是同一个维度，只处理一次。以前写两遍时，merge 第二遍会把 `InhabitedTime` 改成 0（随后 fixer 会把这些区块整块删掉），计划刻、POI、实体也会再追加一遍。
- **`new` 没有 `poi/`、`entities/` 文件时，现在真的会新建。** 以前会把“文件不在”当成“读不出来”跳过，`now` 的 POI 记录和实体就没搬过去；`now` 没有这些文件时也不再算进“坏实体/坏POI”。

规则（新的在前）：

- **玻璃板/铁栏杆的连接、栅栏门贴墙、箱子配对、雪地草、紫颂植株的连接也照游戏重算**（只改样子，不拆）。玻璃板/铁栏杆连别的玻璃板/铁栏杆、墙和整面的方块（不连栅栏和栅栏门）；栅栏门门板两头有墙就放低（`in_wall`）；箱子：单箱旁边是指着它的半个大箱子就补成另一半，大箱子的另一半不是同种箱子了就变单箱（指着的是同种箱子但对不上，游戏不动，这里也不动），铜箱子两半的氧化程度对齐，箱子里的东西照留；草方块/灰化土/菌丝上面是雪层、雪块或细雪就是 `snowy`；紫颂植株六个方向是不是连着紫颂。和游戏对拍：455 种方块 31.4 亿种组合 0 差异（除霜冰和流体），这几种都比完整状态。真实 26.1.1 图上和上一步比：主世界多改 218 格草方块（上面盖着细雪却是 `snowy=false`，雪坡生成时没更新），末地 5 格紫颂植株（下面那截被拆了跟着断开），下界一样；第二遍 0 改动。

## 建议怎么跑

目标版本用现在这套规则的话，就是 **26.1.1**。

1. 备份。下面全部只碰副本。
2. 用游戏自己的 **优化世界（Optimize World）** 把游玩图和旧空板升到 26.1.1。`merge` 不升级方块数据，它是按名字原样搬的。
3. 用 26.1.1 准备一份新空板（`new`）。这是输出，会被改写。种子、出生点、玩家数据都留在 `now` 里，本工具不搬 `level.dat` 里的这些字段，也不搬 `playerdata/`、`advancements/`、`stats/`。
4. `merge`：把 `now` 里相对旧板改过的方块搬进 `new`。
5. `fixer`：按规则拆掉撑不住的方块，并做下面说的清理。
6. 再进一次游戏或再跑一次优化世界，让游戏把被删掉的光照和高度图补回来。

**顺序只能是 merge → fixer，而且只走一趟。** `fixer` 拆掉或换成水的方块，在 `now` 里还是原样；再跑 `merge` 会把它们搬回来。

`merge` 会把每个处理过的区块的 `InhabitedTime` 改成“这一趟搬了几个方块”。一个方块都没搬就是 0。紧接着的 `fixer` 在范围盖住整块时，会把 `InhabitedTime` 为 0 的区块整块删掉（里面的新地形也一起没）；**缺少这个字段、或者不是数，游戏当 0，fixer 也当 0 删**。不想让没改过的地形被删掉，就不要用一份盖满全高的范围去跑 `fixer`，或者跑之前确认你接受“没住过的区块交给游戏按种子重生成”。

## 编译

需要 `g++`（C++23）、`zlib`、`lz4`、`xxhash`（开发包，Fedora：`zlib-devel lz4-devel xxhash-devel`）、`libdl`。程序用 `-Wl,-rpath,'$ORIGIN'` 找同目录的 `libnbtrw.so`，整个目录拷走就能跑。

```sh
make                # 全编：libnbtrw.so、nbtrw、每个 rules.cpp.<版本> 编出的 rules.so.<版本>、merge、fixer
make nbtrw          # 只要 libnbtrw.so 和 nbtrw
make blockporter    # 只要规则插件、merge、fixer（libnbtrw.so 没编会先编）
make rules          # 只重编规则插件（rules.so.26.1.1、rules.so.26.3…）
make rules.so.26.3  # 只编某一个版本的
make clear          # 清掉上面这些编译产物
```

`fixer` 用最后一个参数给的插件，不给就用当前目录的 `./rules.so`（`make` 不建它，要用就自己 `ln -sf rules.so.26.1.1 rules.so`）。

## merge：把改过的方块搬过去

```sh
./merge <new> <now> <old[,old...]> <x1> <y1> <z1> <x2> <y2> <z2> [dims]
```

| 参数 | 说明 |
|---|---|
| `new` | 新版本空板，**输出，会被改写**。目录里要有读得懂的 `level.dat` |
| `now` | 要升级的游玩图，只读 |
| `old` | 旧版本空板，只读。多个用逗号隔开。一个都没有就写 `""` |
| 六个坐标 | 方块范围的两个角，谁大谁小都行，**两头都包含**。必须是 int32 整数，写错直接退出。搬方块严格按它，范围外只读不写；范围碰到的区块 `InhabitedTime` 都会被覆盖。范围给到整个世界也行：没有 region 文件的区域直接跳过 |
| `dims` | 可选。逗号隔开，默认 `minecraft:overworld`。原版三个维度写 `overworld`、`the_nether`、`the_end` 即可（可加 `minecraft:`）。其它字符串当成相对存档根的维度目录。指向同一个目录的写法只处理一次 |

```sh
# 主世界，整区块。有一块旧空板
./merge ./new ./now ./old -1000 -64 -1000 1000 319 1000

# 没有旧空板：now 和 new 不同的方块都会搬（这是写入，不是预览）
./merge ./new ./now "" -1000 -64 -1000 1000 319 1000

# 三个维度，两块旧空板
./merge ./new ./now ./old1,./old2 -1000 -64 -1000 1000 319 1000 \
        overworld,the_nether,the_end
```

每一格的判断：

- `now` 和 **任意一个** `old` 相同，或者和 `new` 自己相同：留 `new` 的。
- 否则算玩家改过，把 `now` 的方块写进 `new`。
- 比较包含方块实体。箱子里的东西、告示牌上的字变了，也算改过，会跟着方块一起搬。
- 没有 `old`（参数是 `""`）时，只和 `new` 比。某个 `old` 读不出来就忽略那一个，不因此整趟失败。

一块地要 **`now` 和 `new` 都有、生成状态都是 `minecraft:full`（26.4 起字段名是 `status`）、区块坐标（`xPos`/`zPos`）也对得上、区块结构没有坏到读不出来** 才会处理。对不上或读不出来就跳过这一块，不新建区块。**不补段**：`new` 里这一段 section 不在（或者没有 `block_states`）的格子跳过，日志里记“缺段跳过”。
跨版本只做暴力合并：`now`、`new`、各个 `old` 的版本（level.dat 的和区块自己的）可以都不一样，方向不限，只管搬运。方块按各自的格式读、按 `new` 那块的格式写，**名字和属性不升级**：1.13 以后正式版之间改过名的方块只有十来种（例如 1.20.3 `grass`→`short_grass`、1.21.9 `chain`→`iron_chain`，完整列表在 ReadMeDeveloper），玩家改过的这几种方块搬过去还是老名字。`old` 最好用和 `now` 同版本的空板，这样没改过的格子不会因为写法不同被误搬。方块实体、计划刻的内容原样搬。实体和 POI 先按 `now` 的版本读出来、再按 `new` 的版本写进去：实体在 1.17（DataVersion 2681）以前存在区块里、之后在 `entities/` 里，两种都认；POI 从 1.13 到 26.3 都认：`new` 是 19w09a 以前的版本（1.13 等，还没有 POI）就不搬 POI、也不建 `poi/`，1.14 快照的老写法也认。单条实体/POI 的内容不改写。默认属性不写导致的多搬、老名字原样搬过去，是已知的特性。
段的 `Y` 照游戏的规矩读：不是 Byte 的数值截成 byte、缺了当 0，同一个 Y 有几段时取最后一段；merge 不改这些，修成合法是 fixer 的事。

处理过的区块还会：

- 把 `now` 里落在范围内的 `block_ticks` / `fluid_ticks` **追加**到 `new`（不去重）；
- 把对应的实体 **追加**到 `new`（不去重）；POI 记录按位置放进 `new`：同一格 `new` 原来有的会被 `now` 的换掉（游戏一格只认一条），票数原样；
- 如果 `now` 有 POI/实体而 `new` 没有对应的 `.mca` 文件，会为已经处理到的区块新建
  `poi/` 或 `entities/` 文件；**不会新建 region 文件/区块**；
- `new` 里对应的 POI/实体块如果读不出来（自定义压缩、坏压缩、坏 NBT 等），只跳过这一块，绝不当成“没有这块”去新建/覆盖；`now` 源块读不出来也一样跳过；
- 把 `InhabitedTime` **覆盖**成这一趟搬过去的方块数（写成空气也算一次）。

不删光照，不删高度图，不整理重复的 section，不清空文件。这些是 `fixer` 的事。读不出来的区域文件不写也不删。终端是 tty 时，merge 会在 stderr 画区块进度条。

逐格比较用 `get_BlockRef` + `equal_BlockRef` 的零拷贝路径，比较语义和 `get_Block` 的
`Block` 相等完全一致；只有确定要写的格子才构造 `Block`、才碰调色板。输出内容不变，
只省掉每格两份深拷贝和重复哈希。

## fixer：拆掉不该留的，并清掉残块和坏索引

```sh
./fixer <path> <x1> <y1> <z1> <x2> <y2> <z2> [dims] [rules]
```

`dims` 和 `merge` 同一个意思；`rules` 是规则插件的路径，不给就用当前目录的 `./rules.so`（要给 `rules` 就得先写 `dims`）。`path` 既是输入也是输出。没有试运行：要先看结果，就复制一份存档再跑。

范围：判物理、单条计划刻/POI/实体记录、迁移错位的方块实体/计划刻严格按给定的 x/y/z；删区块、删光照/高度图、整理区块按 x/z 碰到的区块整块做（**y 不管**）；
整理区域文件（清表头上偏移异常的格子、删空文件、压紧）按碰到的区域文件做。范围外只读不写，只有光照是例外（见下面第 4 步）。

```sh
./fixer ./new -1000 -64 -1000 1000 319 1000 overworld ./rules.so.26.1.1
./fixer ./new -1000 -64 -1000 1000 319 1000 the_nether,the_end ./rules.so.26.1.1
./fixer ./w263 -30000000 -2048 -30000000 30000000 2047 30000000 overworld,the_nether,the_end ./rules.so.26.3   # 整个世界
```

启动时会核对插件的 DataVersion 和 `level.dat`。对不上就什么都不改、直接退出。

存档里可以混着没升级的老区块（每个区块根上有自己的 DataVersion）：

- 1.13 扁平化（DataVersion 1451）以前的、或者没写 DataVersion 的区块：修 NBT、删区块、光照、计划刻、POI 都不碰它，日志记“版本不认识跳过”；
- 和规则插件版本不一样的区块（例如 26.1.1 存档里还是 1.21.5 格式的区块，有的方块后来改了名）：修 NBT、删区块、光照照做（按它自己的格式），规则不判（不拆不改，日志记“版本和规则不同跳过”）、计划刻不拿方块对（留着）、POI 不按方块补删；
- POI 文件的 DataVersion 和规则插件不一样的区块：POI 不动（写回会改掉 DataVersion，游戏就不再升级它）。

它按这个顺序做。总的规矩是**以游戏为准**：游戏读档时会报错（ERROR/WARN）的数据，按最小的单位删掉；游戏不报错、照常读的，一律不动。具体哪些情况怎么处理，开发文档 1.10 有一张对照表。

0. **修 NBT。** 先把每个区块修成游戏读得进来的样子，后面的规则判定看到的是修好的区块：
   - 解压不了、NBT 解析不了的区块：游戏读不进来、会重新生成，整块删掉，`entities/`、`poi/` 同一格一起删（表头上偏移异常的格子游戏当没有，最后整理文件时清成 0）；
   - 游戏的 NBT 读取读不了的值（嵌套超过 512 层、字符串不是合法的 modified UTF-8）：只删那一个值；
   - 某一段的 `block_states` 坏到游戏解不出来（调色板缺了或空了、多种方块却没有 `data`、`data` 长度不对、下标指到调色板外面）：游戏会让整块载入失败，这里只删这一段的 `block_states`（这一段在游戏里就是全空气），别的段保住；`biomes` 同理；
   - 调色板里认不出名字的条目：游戏换成空气，这里也换成空气；
   - `block_ticks`/`fluid_ticks` 不是列表的删掉这一项，单条记录读不进来（名字写法不对、坐标不是数）的删那一条；坐标是别的数值类型（例如 Short）游戏照读，留着；
   - 方块实体没有 `id` 或 `id` 写法不对的删那一条；
   - 方块实体、计划刻的坐标指到别的区块的（范围里的）迁到那个区块：目标区块没有就删这条，目标那一格已经有了留原来的、删这条，读不出来原样留着；没有坐标的、整个区块挪过位置跟着区块走的改到本区块里；
   - 结构引用/起点的名字写法不对的删那一项，结构引用指到 8 个区块以外的删那个坐标；
   - `xPos` / `zPos` 按文件里的位置重写。`sections` 不是列表时游戏当没有段，不动。
   名字游戏认不认识（要用游戏的注册表）、方块实体和方块对不对得上，这次先不查。

1. **规则。** 逐格问 `rules.so`。撑不住的拆掉，或改状态（例如藤蔓关掉贴不住的那一面）。拆掉后留下什么、要不要补计划刻由规则插件给：26.1.1 的插件对含水方块和霜冰写水源并补一条 `fluid_ticks(i=minecraft:water, t=5, p=0)`，和游戏自己拆含水方块一样，避免在水里留洞；别的写空气。含水的栅栏/墙/玻璃板/箱子改了样子也补同样一条（游戏更新它的样子时也排）；箱子改样子时方块实体（里面的东西）照留。每次写方块前会先删这一格旧的 `block_ticks` / `fluid_ticks`。不改 `InhabitedTime`。连锁只看六个面。
2. **删区块 / 修子区块。**
   - 生成状态（`Status`，26.4 起 `status`）不是 `minecraft:full`（没有这个字段也算）：这一块删掉。
   - 里面没有非空气方块，**或者** `InhabitedTime` 是 0：整块删掉。`InhabitedTime` 没有这个字段、或者不是数，游戏当 0，这里也当 0 删（不再补字段）。
   - 删区块是区块级的：x/z 只要沾到范围就整块看，不管 y。
   - 删掉的区块，`entities/`、`poi/` 里同一格一起删。
3. **Y、重复段、调色板**（在最后整理文件时做，整趟一遍）。段的 `Y` 不是 Byte 时照游戏的读法改成 Byte（数值截断，缺了补 0），不删段。同一个 Y 有多段 section 时只留最后那段（游戏读的就是它）。`format_Chunk` 还会把 palette 里没被 `data` 引用的条目压紧，并重写 4096 个下标。
4. **光照和高度图。** 范围碰到的区块删掉 `Heightmaps`，并删 `BlockLight` / `SkyLight`、把 `isLightOn` 写成 0，进游戏后由游戏重算。范围外的区块（包括紧挨着的邻居）一律不动。
5. **计划刻。** `block_ticks` / `fluid_ticks` 先删“缺字段/类型不对”的单条记录，再删“指向的方块和记录类型对不上”的记录；删完同一位置还有多条合法记录时只留一条：**`p` 最小优先，`p` 相同取 `t` 最大**。`block_ticks` 和 `fluid_ticks` 分开算，范围外不动。
6. **POI。** 游戏解不出来的段（没有 `Records`、`Records` 不是列表）删掉这一段，不再整块重建。按 `rules.so` 的方块→默认 POI 表校验：单条记录 `pos` 不是 3 个数、`type` 写法不对的只删这一条（没有 `free_tickets` 游戏当 0，照留）；类型/票数对不上、方块已不该有 POI 的记录删掉；同一位置重复只留 `free_tickets` 最小的一条；缺失的按表补一条默认记录（例如床 `home/1`、钟 `meeting/32`、工作站 `1`、蜂巢/磁石/避雷针/传送门 `0`）。床只认 `part=head`。范围外记录原样保留。0 字节 POI 文件按空区域重建，没东西可补就删文件。删光了就删掉这个 POI 区块；文件空了就删文件。
7. **实体。** 实体区块的 `Position` 坏了或对不上，按文件位置重写（游戏照样载入里面的实体），不再整块删；`Entities` 不是列表的删掉这一项。单条实体 `id` 写法不对、`Pos`/`Motion`/`Rotation`/`UUID` 形状不对、位置是 NaN、朝向不是有限数的只删这一条；没有 `UUID`、没有 `Pos` 的游戏照读，留着。乘客一个个看，坏的只删那个乘客。范围内 UUID 重复时，留下先出现的，删掉后面的（乘客也算）。坏记录删光就删掉整块实体。
8. **POI/实体与 region 对齐。** `region/` 里没有的区块，`poi/`、`entities/` 里同一格的块删掉；**不新建 region**。如果 region 文件本身是 0 字节，会在其它阶段读它之前先删掉，再按“这个 region 没有区块”处理，避免留下孤儿 POI/实体。
9. **区域文件。** 这次碰到的 `region/`、`poi/`、`entities/`：0 字节文件直接删；表头上偏移异常的格子清成 0；一个区块都没有了就删文件；
   `region/` 里范围碰到的区块在这里整理一遍（第 3 步）；最后按顺序压紧（去掉空洞）。数据坏的格子（长度字段对不上）原样搬，不让整理失败。

fixer 各阶段在终端（stderr 是 tty）画进度条。

**坏数据分两类。** 文件级读不出来/写不进去（权限、IO 错、目录冒充文件、截断到读不出头部）：只打日志，单列 `IO跳过`，不改文件、不当成空区域。文件能读但区块 NBT/结构坏：`fixer` 按游戏会不会报错、按最小单位删（单条刻/POI/实体记录、坏掉的一段 `block_states`，只有游戏整块读不进来的才删整块），`merge` 整块安全跳过，都不写半份数据。区域文件表头不满 8KB 时，游戏只警告、照读读到的部分，这里也照读，整理时把表头写全。区块压缩支持 gzip/zlib/不压/lz4，外置的 `.mcc` 也能读写；模组的自定义压缩（类型 127）读不了，只记日志、跳过，不按坏块删。

`fixer` 每个维度打印三行统计：物理（判了几格、拆/改了几格、读不出、`版本和规则不同跳过`…，后面跟着每条规则改了几格、改得最多的方块）、修 NBT（读不了的值、坏 `block_states`/`biomes` 段、认不出的调色板条目、坏刻表、坏方块实体、坏结构引用/起点、迁走/删掉/留着的错位方块实体和计划刻）、清理：删区块（含 `坏NBT`）、光照/高度、计划刻删/坏记录/重复、POI 删/补/重复/坏记录/坏块/块/文件、实体删/坏记录/块/文件、改坐标/重复段/改Y段/压调色板、删空 MCA/format/清偏移异常、`IO跳过`、`版本不认识跳过`、失败。失败非 0 时进程返回非 0；`IO跳过` 只记录，不算处理失败。`merge` 会打印搬运方块数、计划刻/实体/POI、跳过区块和坏区域/坏实体/坏POI/存盘失败。

## 规则插件在判什么

现在有 `rules.so.26.1.1` 和 `rules.so.26.3`。换一套同 ABI 的插件：把它的路径给 fixer 的最后一个参数就行，不用重编 `fixer`。自己写插件的接口在 `rules.hpp`，必须用同一套 g++ / libstdc++ 编。兼容性看 `RULES_ABI` **和** `sizeof(Rules_Api)`；改了接口就把 `RULES_ABI` 加 1，旧插件会装不上。当前 ABI 是 NBR7（`0x4e425237`）。ABI 只跟 `rules.hpp` 走（fixer 和插件之间怎么调用），不跟 rules.cpp 的版本走：一个 fixer 配不同的 `rules.so`，修不同版本、不同模组的存档。fixer/libnbtrw 只管存档格式（按 DataVersion），方块知识（支撑、流体、默认属性、POI、拆完留什么、计划刻对不对得上）全在插件里；插件内部的数据放在 `Blk_Info::priv`，主机不解释。插件入口符号是 `get_RulesApi`。

规则只看这一格和六个面，不再去读斜下方。拿不准就留着：**宁可漏拆，不拆玩家搭的东西。** 插件不能放方块；改状态（关面、换成别的状态、照邻居重算样子）要能保证每格只改有限几次（`rules.hpp` 文件头写了三种允许的改法和证明），否则 `fixer` 可能停不下来。

26.1.1 这版和旧规则相比，使用时要注意：

- **支撑按面算，照游戏本身。** 每个方块状态都算好六个面各自能给什么支撑（整面 / 中心 / 顶面带边 / 碰撞面），和游戏逐个状态对过；再按原版那一类方块用的判法查：
  - 门、海草、墙上火把、按钮、梯子、珊瑚扇、钟乳石、绊线钩、垂根、洞穴藤蔓、缠怨藤/垂泪藤、苍白垂须要**整面**；火把、灯笼、吊牌、孢子花要**中心支撑**；铁轨、中继器、比较器要**顶面带边**（炼药锅、堆肥桶、漏斗也算），压力板是带边或中心都行，红石线是整面或漏斗。
  - 告示牌、旗帜、蛋糕看下面（或背后）是不是**实心方块**，按英文放置页的定义：强制实心名单（灯笼、压力板、海龟蛋、潮涌核心、锁链、失活珊瑚、紫水晶簇……）、强制不实心名单（杜鹃、大型垂滴叶、紫颂、梯子、雪），其余按碰撞箱大小。栅栏、楼梯、门、其它告示牌上都行，末地烛、脚手架上不行。仙人掌旁边是不是实心也按这个。
  - 藤蔓、发光地衣、幽匿脉络、树脂团看那一面是**整面或者碰撞箱满**，所以能贴树叶，不能贴栅栏、耕地侧面；雪层看碰撞箱顶面，树叶上能积雪。**藤蔓挂在下面看的是上方方块的顶面**（游戏就是这么写的）：上半砖、倒楼梯、上半活板门、脚手架下面能挂，下半砖、耕地、营火、讲台下面不能挂；发光地衣看的是上方方块的底面。藤蔓侧面只认背后能贴、或者上面那格是同一面的藤蔓，旁边是藤蔓不算。苍白垂须挂在整面或树叶下面，也能接在另一条下面。
  - 例子：上半砖只有顶面算整面，下半砖只有底面算；楼梯的背面是整面，内角楼梯再加左边或右边那一面（看 `inner_left`/`inner_right`）；门、开着的活板门、梯子、展示架只有贴着的那一面是整面；中继器、比较器、地毯底面是整面；沉重核心只有底面中心；树叶什么都撑不住（支撑形状是空的）；仙人掌、蜂蜜块顶面撑不住东西；炼药锅顶面只有一圈边；耕地、土径、讲台、附魔台、幽匿感测体/尖啸体、沉重核心只有底面是整面；脚手架顶面是整面；**紫颂花什么都撑不住**（23w31a 起，英文放置表那一行是旧的）；末地烛、避雷针、嗅探兽蛋、吊牌（天花板上和墙上的都算）顶上能放火把。
  - 依据的顺序：游戏本身（原版 jar 对拍）＞反编译源码＞wiki。wiki 和游戏说法不一样时按游戏（英文放置页三张表里这样的格子都在 `test/check_placement.py` 的 `KNOWN` 里写了原因）。
- **重力方块照游戏判。** 沙子、红沙、沙砾、可疑沙/可疑沙砾、铁砧（含破损）、龙蛋、混凝土粉末，正下方是空气、火、液体（水/岩浆/气泡柱）或**可替换方块**（草、蕨、雪层、藤蔓、发光地衣、幽匿脉络、树脂团、海草、枯灌木、落叶层、垂根……，游戏的 `FallingBlock.isFree`）就拆掉，**不生成掉落物**（游戏是让它落下去；fixer 只能拆不能往别处放）。含水方块（泡水的台阶等）不算液体，托得住。
- **混凝土粉末**先看上面和四个侧面有没有能碰到的水，有就变成对应的混凝土；没有才按上面的重力规则判。正下方的水不算（游戏也不算），所以浮在水面上的粉末是掉。
- **霜冰**一律换成水（冰霜行者刚踩出来、还没化的也会被化掉）。
- **落叶层**要下面顶面完整（25w06a 改成过中心支撑，25w09a 又改回来了），栅栏上的会拆；**雪层**要求下面碰撞箱顶面完整，开着的活板门/漏斗不算，树叶算。
- **龟蛋可以撑住挂在它下面的灯笼**；`copper_lantern` 归薄片（不能反过来撑火把）。附生西瓜/南瓜茎只认 farmland。
- **仙人掌**四周有实心方块或岩浆、或者上面是水/岩浆/气泡柱就拆；**睡莲**和**青蛙卵**要下面是水源（含水方块也算，流动水不行），睡莲还可以放冰上；**蜡烛**只有放的时候要支撑，支撑没了会悬着（中文 蜡烛），不拆；**海泡菜**要下面顶面有碰撞箱（水、耕地、2~7 层雪上不行）；**蘑菇**要下面顶面完整且整块不透明（冰、玻璃、树叶、屏障不行，浮冰可以）；**瓶子草作物** age 0~2 只有一格高，不要求上半。
- **珊瑚**（不是扇）、插蜡烛的蛋糕、树脂团这次加进了规则表。
- **村民工作站、蜂箱、磁石、炼药锅这类兴趣点方块**游戏里不需要支撑，悬空也留着；缺失的 POI 记录会按 `rules` 的默认表补。**床**也不需要下面的支撑，但两半互相要：另一半不是同一种床就拆。钟按挂法检查，贴墙的钟支撑在它 `facing` 那一侧。
- **两格高的东西两半互查**：门（另一半是别种门也留着，游戏会把它改成那种门，规则不改）、高草/高花、小型垂滴叶；大型垂滴叶茎上面要是茎或叶子；活塞头背后要是对应的活塞。
- **中低优先级的也按游戏收了**：紫水晶要求完整面（树叶、蜂蜜块、紫颂花都没有）；压力板是带边或中心（树叶上不行）；栅栏门**底下**不提供中心支撑（顶上照旧能放火把）；脚手架照游戏现算距离（下面是脚手架取它的距离，下面是别的方块且顶面整面就是 0，旁边的脚手架距离 +1，取最小，到 7 就拆）；海带要求下方完整顶面且不是岩浆块。
- **故意和游戏不一样的**：霜冰见到就化成水（你定的）；规则只看六个面，看不到的（甘蔗旁边的水、紫颂旁边那株的根、光照、整个传送门框）都当成能活；流体不管（流动水游戏自己按流体刻慢慢算）；“只是样子”的属性里，楼梯形状还没做（以后照游戏做），红石线连接要看斜对角的格子、红石信号不重算；别的（栅栏/墙/玻璃板的连接、门、箱子、滴水石锥粗细、树叶的 distance……）都照游戏重算。
- **紫颂植株**“旁边连着紫颂、上下都不空”照游戏拆（末地自然生成的树里有极少数这种格子，游戏下一次方块更新也会拆）；旁边那株的根在斜下方，看不到，横枝留着。
- **外观转换照游戏做**：门两半照对方改（谁先被判谁照对方改，改完一致）；藤头/藤身、大型垂滴叶叶子/茎、竹笋/竹子、竹子的 age、火的朝向面、火→灵魂火；栅栏/墙/玻璃板/铁栏杆/紫颂植株的连接、苍白苔藓地毯的侧面、栅栏门贴墙、箱子配对、雪地草（见上面“规则”前两条）。

## nbtrw：看一眼存档，不改它

这是库的 demo，不是修图程序。参数都要写全，没有默认路径。

```sh
./nbtrw nbt   <file.nbt>                       # 打印成 SNBT
./nbtrw nbtw  <file.nbt>                       # 读、编码、再解析，核对编码/深拷贝/比较（不回写）
./nbtrw dat   <level.dat>                      # 读 level.dat
./nbtrw mca   <目录> <rx> <rz> <cx> <cz> [w]   # 读区域里的一个区块；w 会另存 .mca_test.mca
./nbtrw chunk <file.nbt> <x> <y> <z> [方块名]  # 读单区块文件里的一格
./nbtrw level <存档目录>                       # 看 DataVersion、三个维度的区域目录、(0,0) 在不在
```

`level` 适合先确认目录认没认错。维度目录按 DataVersion 选：大于等于 4774 用 `dimensions/minecraft/<维度>/`，否则用老的 `region/`、`DIM-1/`、`DIM1/`。

要在自己的程序里用这个库，包含 `nbtrw.hpp`，链接 `-lnbtrw -lz`。

---

## 它不做什么

- 不升级方块 id，不搬玩家存档、计分板、进度。版本对齐靠游戏的“优化世界”。
- 不模拟原版全部物理。树叶腐烂、珊瑚缺水、冰自然融化、甘蔗旁边要有水、流体流动、重力方块往下掉（现在直接拆）、楼梯形状（以后做），这些不做。霜冰是上面列过的例外。
- POI 只按 `rules` 的表补 vanilla 方块；不猜 mod 的 POI 类型，也不重算已有合法记录的票数。范围外记录不动。
- 不碰读不出来的区域文件；文件能读但区块 NBT/结构坏的，fixer 整块删、merge 整块跳过。
- 不管你在 `fixer` 之后又跑了一次 `merge`。

## 附带：预生成空板

发布仓库根目录的 `gen_raw_map.sh` 用 Fabric 服务端 + Chunky（可选 C2ME）跑一张纯净地图，和 `merge` / `fixer` 没有依赖，可以单独用。`./gen_raw_map.sh -h` 看参数（只在 `nbtrw/` 工作树里、没有这个文件时跳过这一节）。它不检查有没有真的生成完。
