# nbtrw —— 用户手册

MC Java 版存档（`.mca` 区域文件）的直接读写工具，不依赖 amulet 之类的库，也不用开游戏。四个程序 + 一个库：

| 程序 | 干什么 |
|---|---|
| **merge** | 升版本时搬方块：把游玩地图（now）里"相对旧版本改过的方块"搬进新版本空板（new，new 同时是输出）；**顺带把实体（`entities/`）整块搬过去、把兴趣点索引（`poi/`）按合并后的方块修对、把空的区域文件清掉** |
| **fixer** | 扫存档，把浮空/撑不住的方块处理掉（拆掉，或像藤蔓那样只关掉撑不住的那几个面）；**拆掉的是兴趣点方块（钟等）时，把它那条 `poi/` 记录一起删掉** |
| **prune** | 删掉存档里"没生成完/空壳"的残块（`Status != minecraft:full`，或者一个方块都没有的区块），让游戏（或 Chunky）按种子重新生成它们；**Chunky 跳过已存在区块**留下的空洞就靠它治 |
| **nbtrw** | 底层库 `libnbt.so` 的 demo（读 NBT、level.dat、区域文件、区块、存档目录各来一个例子） |
| **libnbt.so** | 上面几个程序共用的底层库；`rules.so` 是 fixer 的规则插件 |

技术细节、设计取舍、踩过的坑在 `ReadMeDeveloper.md`；这里只讲怎么用。

---

## 1. 编译

```sh
make            # 全编：libnbt.so、rules.so.26.1（+符号链接rules.so）、merge、fixer、prune、nbtrw
make rules      # 只重编规则插件（改规则时最常用，fixer/merge 不用动）
make clean      # 删掉所有产物
```

依赖：`g++`（要 C++23）、`zlib`、`libdl`。产物都带 `-Wl,-rpath,'$ORIGIN'`，
所以 `libnbt.so` / `rules.so` / 四个程序放在同一个目录里就能跑，整个目录拷到哪都行。

手工编（顺序别乱，merge/fixer/prune/nbtrw/rules 都要链 `libnbt.so`）：

```sh
g++ -std=c++23 -O2 -Wall -Wextra -pedantic -fPIC -shared nbt.cpp block.cpp chunk.cpp mca.cpp level.cpp -o libnbt.so -lz
g++ -std=c++23 -O2 -Wall -Wextra -pedantic -fPIC -shared rules.cpp -o rules.so.26.1 -L. -lnbt -lz -Wl,-rpath,'$ORIGIN'
ln -sf rules.so.26.1 rules.so
g++ -std=c++23 -O2 -Wall -Wextra -pedantic merge.cpp  -o merge  -L. -lnbt -lz -Wl,-rpath,'$ORIGIN'
g++ -std=c++23 -O2 -Wall -Wextra -pedantic fixer.cpp  -o fixer  -L. -lnbt -lz -ldl -Wl,-rpath,'$ORIGIN'
g++ -std=c++23 -O2 -Wall -Wextra -pedantic prune.cpp  -o prune  -L. -lnbt -lz -Wl,-rpath,'$ORIGIN'
g++ -std=c++23 -O2 -Wall -Wextra -pedantic nbtrw.cpp  -o nbtrw  -L. -lnbt -lz -Wl,-rpath,'$ORIGIN'
```

仓库里那几个 `.c`（`nbt.c` `mca.c` `chunk.c` `dat.c` `nbtw.c`）是当初移植用的 C 参照，**不改**；
它们在 `test/c/` 里，各自都是一个能单独编的程序（各有各的 `main`，别一起编——符号会重）：
`gcc -std=c23 -O2 test/c/nbt.c -lz -o nbt`（`mca.c`/`chunk.c`/`dat.c`/`nbtw.c` 同理）。
这些编出来的二进制不进 git。

## 2. merge：搬方块

```sh
./merge <new_path> <now_path> <old_path[,old_path...]> <x1> <y1> <z1> <x2> <y2> <z2> <chunk_unit> [dims]
```

| 参数 | 说明 |
|---|---|
| `new_path` | 新版本空板，**合并的输出（会被改写）**；目录里要有 `level.dat` |
| `now_path` | 要升级的地图，只读 |
| `old_path` | 旧版本空板，只读，逗号隔开可以给多个；**一个都不给就写空串 `""`**（那就什么都不合并，只统计） |
| `x1 y1 z1 x2 y2 z2` | 方块范围的两个角，谁大谁小都行（内部取 min/max），**含两头临界值** |
| `chunk_unit` | `1`＝以区块为单位（x/z 不裁，整块整块地看）；`0`＝裁到上面的范围里（只认 0/1） |
| `dims` | 可选，逗号隔开的维度名，默认 `minecraft:overworld`；例：`minecraft:overworld,minecraft:the_nether`（同一个维度写两遍也只跑一趟） |

坐标和 `chunk_unit` **必须是整数**：写成 `x1=-1000`、`abc` 或者超出 int32 的数，程序会直接报错退出，
不会像以前那样静默当成 0 去跑另一个范围（fixer/prune 是就地改存档，跑错范围很危险）。

范例：

```sh
# 搬主世界的 (-1000,-63,-1000)~(1000,319,1000)，整区块处理
./merge ./new ./now ./old -1000 -63 -1000 1000 319 1000 1

# 三个维度一起，old 给两个（多版本参照）
./merge ./new ./now ./old1,./old2 -1000 -63 -1000 1000 319 1000 1 \
        minecraft:overworld,minecraft:the_nether,minecraft:the_end

# 只统计、不改任何东西（old 给空串）
./merge ./new ./now "" -1000 -63 -1000 1000 319 1000 1
```

判断规则（原型 `merge.py` 只做了最基本的一条"now 和 old 不一样就搬"，下面这套跳过/`Status`/空壳/`InhabitedTime` 后来才加的）：

1. 一个区块要 **(now 有) 且 (new 有) 且 (至少一个 old 有)** 才动；
2. 一个方块要 **(now 读得出来) 且 (now ≠ new) 且 (now 和所有 old 都不一样)** 才搬过去。
3. 不满足 1 的区块**整块跳过**（方块/实体/兴趣点一个都不碰，只有 `InhabitedTime` 例外，见下面两节）。

**old 给空串时 `new` 一个字节都不会改**：连实体、兴趣点、空文件清理、`InhabitedTime` 清零也一起跳过，只打印统计。
可以拿它当"试跑"看数字（按规则 1，一个 old 都没有时本来也不会搬方块）。

搬完一个区块会删掉 `isLightOn` 和 `Heightmaps`（光照和高度图算不了，交给 MC 运行时自己算），
`InhabitedTime` 严格写成**这一趟搬过去的方块数**（跳过的位置写 `0`，见下面）。`new` 里缺的 section 会补一段空 section（全空气，biome 抄 `now` 的）。

**参数只认位置，没有 `key=value`。** 范围必须 6 个数写全，少写直接报错退出——这是故意的：
写一半会"按默认范围跑"，等于悄悄改了别的区块。缓存槽数、区域镜像数、进度条这些都在程序里定死
（`merge.cpp` 的 `merge_Config`），要改就重编。

几条安全上的"宁可不动"（都会打印出来，而且**退出码非 0**）：

- **区域文件存在但读不出来**（权限不对、IO 错、被截断、名字撞上目录）：那个文件**一个字节都不写**。
  以前这种情况和"文件不存在"同形，会被当成"这里没有区块"，写回去就把没读到的区块整片抹掉；
- **区块的 `xPos`/`zPos` 和文件位置对不上**：整块跳过。方块是按文件位置读写的（自洽），但方块实体是按
  区块自己的 `xPos`/`zPos` 找的，两套坐标一打架就会在错的位置搬/删实体；
- **多个维度一起跑时，任何一个维度失败，整趟就非 0 退出**（不会被后面维度搬的区块数盖掉）。

### 看输出

```
merge: new=./new (DataVersion 4788 26.1.1)
merge: now=./now (DataVersion 3465 1.20.1)
merge: [minecraft:overworld] 区域目录 now=./now/region
r.0.0: 4 chunk(s), 12345 op(s), 0 new section(s), 1.2s
merge: [minecraft:overworld] 合并 4 个区块，12345 次改动，新补 0 段section，失败 0 个，区域存盘失败 0 次，用时 1.3s
```

- `失败 N 个`：多半是那段 palette 满 256 条了（MC 会改用 direct 调色板，这里不支持），这些位置没动；
- **警告：一个区块都没读到**：路径或存档结构不对（DataVersion 和实际目录对不上），先看"区域目录"那几行；
- 结尾如果有 `有失败…`，退出码是 255。

### 跳过：一格方块都不搬的那些情况

merge 对每一格的态度是"要么照规矩搬，要么**整块跳过**"（跳过＝方块/实体/兴趣点一个都不碰）。
跳过一共这么几种，报告里会分类报数：

```
merge: [minecraft:overworld] 跳过 32 个区块（一个方块都没搬）：now那边 mca不存在 1、表里没这个区块 26、
数据读不出来 1、Status不是full 1、没有Status字段 1、full但一个方块都没有 1、xPos/zPos对不上 0；
new里没这个区块 1（不新建）、new那边读不出来 0；old里一个都没有 0
merge: [minecraft:overworld] 跳过的位置把 new 那份的 InhabitedTime 清成 0（这趟清了 31 格；合并的区块那边严格等于搬过去的方块数）
```

| 原因 | 意思 |
|---|---|
| `mca不存在` | `now` 那边连区域文件都没有（那片地没生成过；板子上多出来的部分就是这样） |
| `表里没这个区块` | 区域文件在，但表头那一格是空的：这个区块没生成过 |
| `数据读不出来` | 区块在，但压缩数据/NBT 坏了。坏数据只影响它自己，**这种位置退出码非 0** |
| `Status不是full` | `now` 的 `Status` 不是 `minecraft:full`：C2ME/生成被中断留下的半成品（地形没写完） |
| `没有Status字段` | 区块里压根没有 `Status`（老存档/别的工具写的）。它不是 full，一样跳过（实测真存档里没有这种区块） |
| `full但一个方块都没有` | "空壳"：`Status=full` 但翻 `data` 一个方块都没有——游戏认为它生成完了，**永远不会再补地形** |
| `xPos/zPos对不上` | 存档有毛病（区块坐标和文件位置不一致），宁可不动。**这种位置退出码非 0** |
| `new里没这个区块` | 板子上没有这一格：**不新建**，直接跳过（板子只写它本来有的区块） |
| `old里一个都没有` | 判不出这格是不是玩家改的（没有参照版本），整块不合并 |

前四种就是"`now` 的区块读不到"的四种情形。不跳过的话：空区块的每一格在 `now` 里都读成空气，
相对 `new`/`old` 又都"不一样"，merge 会规规矩矩把 `new` 的方块**写成空气**——新板就被戳出一圈空洞
（而且 `Status=full`，游戏永远不会补）。这些位置不是玩家的东西，所以宁可不动。
`now` 里这种残块很多的话，用 `./prune`（见第 3 节）把它们删掉，让游戏重新生成。

### InhabitedTime：合并的写"搬了多少方块"，跳过的写 0

`InhabitedTime`（区块被玩家"住"了多久，影响本地难度/刷怪）在 merge 里是**算出来的**，不是抄来的：

| 这一格 | 写进 `new` 的值 |
|---|---|
| 合并了 | **这一趟搬过去的方块数**（`0` ＝这趟没搬任何方块，比如第二趟跑） |
| 跳过了（上面表里任何一种，含 `old里一个都没有`） | `0` |
| `new` 里没有这个区块 | 不写、也不新建（见上表） |

所以板子上"进游戏看一眼"留下的那些 tick 值会被抹掉：跳过的地方清 0，合并的地方按搬的方块数重算。
跳过的位置**只在本来不是 0 的时候才写盘**（第二趟跑不会平白重写一遍区块）。

两个要注意的：

- **这是"这一趟"的数字**。同一份板子再跑一趟 merge，因为已经没差异了，合并过的区块会被写成 `0`；
  要留住某一趟的数字，就别重复跑（或者先把 `new` 备份一份）。
- **代价**：因为要确认哪些板子区块的 `InhabitedTime` 不是 0，merge 会把 `new` 范围里的区块**都读一遍**
  （哪怕 `now` 里压根没有这块地）。这是"跳过区域一律 0"的必然开销，比只读 `now` 有的那部分慢；
  读不出来的（坏数据）会照常报数、非 0 退出。

### 实体和兴趣点（`entities/` 和 `poi/`）

26.1 起一个维度有三个同级目录：`region/`（方块）、`entities/`（村民/宠物/展示框/箱车这种**非**方块实体）、
`poi/`（**兴趣点索引**：床、村民工作站、钟、传送门…。村民认领床位/工作站、传送门找出口都靠它）。
merge 除了搬方块，还会处理这两个目录——**不然新图里会一个村民都没有、村民的床和工作站也全不认了**：

| | 规则 |
|---|---|
| **实体** | `now` 里那块有实体数据 → **整块照抄**盖掉 `new` 的（连 `DataVersion` 一起，让游戏自己升级）；`now` 那边是**空表** → 把 `new` 那块**删掉**（不写空表）；`now` 那边没有 → `new` 自己的原样留着。抄之前会核一下形状（`Position` 得对上槽位、有 `DataVersion`、`Entities` 是 list），不对就跳过并计数 |
| **兴趣点** | 候选＝`now` 的记录 ∪ `new` 的记录（**同一位置以 `now` 为准**）；然后拿**合并完那一格到底是哪个方块**去核：方块和记录类型对得上就留（**票数照抄来源，不夹上限**），对不上／认不出／表里没有就**删这条**。一条不剩的区块从文件里删掉，整个文件空了就删文件。**不会**反过来给"有方块没记录"的位置补记录（那是游戏自己该干的事） |
| **顺手清理** | `new` 的 `entities/`、`poi/` 目录里，**0 字节**的、以及**正好只有 8KB 头（一格区块都没有）**的 `r.<x>.<z>.mca` 会被删掉——游戏生成世界时自己会留这种空文件。比 8KB 大、但表头全空的**不删**（数据区可能还有东西），只打一行提醒 |

为什么要"同一位置以 now 为准"而不是把 `new` 那份标脏重算：`free_tickets`（还剩几张票）是**认领状态**的镜像，
标脏会让游戏把票全部重置，**没交易过的村民就会把别人认领的工作站抢走**（wiki：只有 unclaimed 的工作站能被认领）。
所以这里宁可"跟着 now 的票走、对不上的记录单独删"。

`entities/` 和 `poi/` 的落盘顺序是 **方块 → 实体 → 兴趣点**：万一中途失败/断电，宁可"方块写进去了、索引还指着旧的"
（下一趟 merge 会照着方块把索引修对），也别反过来变成"索引说有床/村民、方块却没写进去"。

**前提**：`now` 和 `old` 都要先被游戏自己（DFU/数据修复）升到目标版本再拿来合并——POI/实体的字段名和布局
跟着游戏版本走，merge 只负责搬，不做字段升级。`now`/`old` 全程只读（merge 只写 `new`）。

## 3. prune：删掉没生成完/空壳的区块

```sh
# 只统计（一个字节都不改）：看看这块地上有多少残块
./prune <存档> <x1> <z1> <x2> <z2> 0
# 真删（一般先在副本上跑一遍 mode=0，再在副本上跑 mode=3）
./prune <存档> <x1> <z1> <x2> <z2> 3
# 三个维度一起
./prune <存档> 0 0 511 511 3 minecraft:overworld,minecraft:the_nether,minecraft:the_end
```

| 参数 | 意思 |
|---|---|
| `x1 z1 x2 z2` | 方块范围的两个角，谁大谁小都行（内部取 min/max，整区块处理） |
| `mode` | `0`=只统计；`1`=只删"没生成完"的（`Status != minecraft:full`）；`2`=只删"空壳"的（一个方块都没有）；`3`=两种都删（一般用这个） |
| `dims` | 可选，逗号隔开的维度名，默认 `minecraft:overworld` |

### 什么时候要用它

**Chunky（以及"在已有世界上接着跑"的生成流程）认为"盘上有这个区块＝已经生成过"，会跳过它。**
如果盘上留下的是两种残块，那一圈就永远不会长地形，地图中间就是一个空洞（人走进去看得见、怎么加载都不补）：

1. **没生成完**：`Status` 停在 `structure_starts`/`biomes`/`carvers`/… 的半成品，地形根本没写；
   （C2ME 会先把这种"proto chunk"落盘，生成被中断/机器被杀就会留下来）
2. **空壳**：`Status=minecraft:full`，但里面一个方块都没有 —— 最坑的一种，**游戏认为它早就生成完了，
   永远不会再补**（`prune` 是翻 `data` 数方块来判断的，光看调色板看不出来：调色板里可能还留着石头）。

`prune` 把残块从区域文件里删掉（表头那一格清 0）＝这块地重新变成"没生成"，
下次进游戏 / 下次 `chunky start` 就会老老实实按种子生成。
删的一定是残块（玩家玩过的地方一定是 `Status=full` 且有方块），所以不会丢东西；
删区块时 `entities/`、`poi/` 里对应的那一格一起删，免得留下指着空洞的索引。

### 输出怎么看

```
prune: [minecraft:overworld] 看了 5 个区块：没生成完 1 个、空壳（一个方块都没有）2 个
prune: [minecraft:overworld] 删了 2 个区块（其中没生成完的 1 个、一个方块都没有的 2 个，两样都占的会重复计），
                             顺带删 entities 索引 2 个、poi 索引 2 个，删空文件 0 个
prune: [minecraft:overworld] 这些格子现在等于"没生成"，进游戏/跑一次chunky start 就会按种子重新生成
```

规矩和其它程序一样：**读不出来的区域文件一律不碰**（报出来、退出码非 0）；没有 `Status` 字段的区块
（老存档/别的工具写的）算"认不出来"——`mode=1` 不会删它。要改就先在副本上跑。

## 4. fixer：修浮空物

```sh
./fixer <path> <x1> <y1> <z1> <x2> <y2> <z2> <chunk_unit> [dims]
```

| 参数 | 说明 |
|---|---|
| `path` | 要处理的地图目录，**既输入也输出（会被改写）** |
| `x1 y1 z1 x2 y2 z2` | 方块范围，同 merge（含两头临界值，内部取 min/max） |
| `chunk_unit` | `1`＝整区块处理（x/z 不裁）；`0`＝裁到范围里（只认 0/1） |
| `dims` | 可选，逗号隔开的维度名，默认 `minecraft:overworld`（同一个维度写两遍也只跑一趟） |

坐标同样是"必须是整数、写错直接报错退出"（见 §2 的说明）。

范例：

```sh
./fixer ./now -1000 -63 -1000 1000 319 1000 1                    # 主世界
./fixer ./now -1000 -63 -1000 1000 319 1000 1 minecraft:the_nether,minecraft:the_end
```

**改之前先备份**：fixer 是就地改的，没有"试运行"开关。想先看会改什么，就复制一份存档先跑那份。

它会一上来打印一行插件信息，然后每个维度一行统计：

```
fixer: 规则插件 /path/rules.so（版本26.1，22条规则、5个规则家族）
fixer: ./now DataVersion=4788（26.1.1），存档结构=dimensions/新（阈值 4774，见level.cpp）
fixer: [minecraft:overworld] x[-1000,1000] y[-63,319] z[-1000,1000] 区域目录 ./now/dimensions/minecraft/overworld/region
fixer: [minecraft:overworld] 扫了 1112 个区块、3555 段（有要管的方块的 812 段）、初扫判了 42000 个位置（算上连锁一共判 42100 个）；拆掉 4915（其中 3 个原来含水，换成水不是空气）、改状态 120、写不进去 0，共 5035 次改动，用时 4.8s
fixer: [minecraft:overworld] 全量扫完+就地连锁补完，已收敛（不用复扫）；连锁就地补判 100 个位置、又改出 16 个；真读了 900 次区块（缓存256槽；另有 12 个坐标是空的，记下来不重试）
fixer: [minecraft:overworld] 按规则分（判过/改动）：
fixer: [minecraft:overworld]   下面要有支持       21000 / 4200
fixer: [minecraft:overworld]     └ 改的是：short_grass×3800, fern×300, dead_bush×100
...
```

- **`已收敛（不用复扫）`** 是可以放心的信号：全量扫完 + 连锁队列判空 ⇒ 已经到不动点，再跑一遍是 0 改动；
- **`按规则分` 下面那行 `└ 改的是：…`** 是每条规则**实际拆掉了哪些方块**（改动最多的前 6 种）。
  跑正式存档前扫一眼这行：某条规则拆了一大片你没想到的方块，就是规则表该复查了
  （真事：`big_dripleaf` 的叶子长在自己茎的顶上，表里漏了这条，一张区域就误删 1455 片叶子）；
- `拆掉的POI方块：删了 N 条记录，M 个区块清空后删掉，K 个空文件删掉`：拆掉的方块如果是兴趣点方块
  （钟、讲台、砂轮这种），它在 `poi/` 里那条记录会一起删掉——留着就是"指向空气的索引"，村民会跑去找一个
  不存在的工作站。记录删光的 POI 区块从文件里删掉，整个文件空了就删文件；
- `有 N 个位置要用的邻居读不出来`：区块没生成、或者调色板是 direct 那种，这些位置原样留着没判（宁可漏拆）；
- `有 N 段读不出调色板（direct/>256条）、M 个位置的数据缺/短`：前一种本程序有意不读（只报数），
  后一种是坏数据，会让退出码非 0；
- `有 N 个区块的xPos/zPos和文件位置对不上`：存档有毛病，整块跳过没动；
- `有 N 个区块里出现了两段Y相同的section`：坏数据，整块跳过——那种情况"判A段、写B段"会删掉没判过的方块；
- `有 N 次要改的东西本来就那样`：正常应该是 0，不是 0 说明规则表或插件有问题（已经跳过没写，不跳会转不完）；
- `POI区域文件 r.x.z 读不出来`：方块拆了但记录删不掉，退出码非 0（文件一个字节没动）；
- 每个维度扫完会存一次盘（区域为单位），结尾再存一次。

被拆的方块去哪儿了：普通方块 → 空气；原来**含水**的（`waterlogged=true`，或者海草/海带/珊瑚这种泡在水里的）
→ `minecraft:water`（`level=0`）。写空气会在水底留洞，还会让旁边靠这格水活着的东西白丢水源。

**霜冰（`frosted_ice`）会化成水**（规则插件里的 `RULE_FROST`，归在 `misc` 家族）：它是冰霜行者靴子踩过水面时
生成的临时方块，原版过一会儿自己就化了——wiki [Frosted Ice](https://minecraft.wiki/w/Frosted_Ice)：
*"When the age reaches 4, the block turns into water"*。服务端出问题时会把这种方块成片写进存档
（本该早就化掉的），fixer 见到就换成水源（`minecraft:water[level=0]`）：**不看支撑、也不判光照**——
光照图我们读不到，而且 wiki 说低光照的地方（地下、夜里、末地）它本来就赖着不化。
**代价**：玩家穿着冰霜行者靴子刚踩出来、还没化的霜冰也会被一起化掉（那本来也是要化的，只是早了一点）。
不想要这条规则的话，换一个不带它的 `rules.so`（见第 5 节），或者把范围避开刚踩过的水面。

**紫颂（末地那种树）严格照原版判**（`RULE_CHORUS` / `RULE_CHORUS_PLANT`，依据是 26.1.1 的
`ChorusPlantBlock.canSurvive`，也就是 wiki [Chorus Plant](https://minecraft.wiki/w/Chorus_Plant) 的 "Support" 那两条）：
紫颂树是"横着伸一格、再从那格往上长"的，所以**横枝底下天生就是空气**，靠的是旁边那一株"有根"
（它自己下面也是末地石/紫颂植株）撑着——判它要读旁边那株的**斜下方**那一格。因此一块原版生成的末地
（整张图 34315 个区块、16 万多个紫颂方块、判了 165010 个位置）跑完是 **0 改动**；
要是你的末地跑出成百上千个"紫颂植株/紫颂花"，
先别当真，多半是规则出了问题（这一条正是被真图跑出来的，经过见 `ReadMeDeveloper.md` 6.12）。
只有一处我们**故意比原版宽**：原版还规定"水平挨着紫颂、上下又都不是空气"的紫颂植株会碎，
而末地自然生成的地形里就有极少数这种格子（1024 个区块约 4 格；原版要等下一次方块更新才把它拆掉）——
fixer 不替原版做这件事，免得"修完末地少了几棵树"。想严格照原版，就把 `rules.cpp` 里的
`CHORUS_PLANT_STRICT` 改成 1 重编 `rules.so`。

拆掉的方块如果正好是**兴趣点方块**（床、村民工作站、钟、传送门、蜂巢…，见 `poi/` 那一节），
它在 `poi/` 里那条记录也会一起删掉——留着就是"指向空气的索引"，村民会跑去找一个不存在的工作站。
**只删 fixer 自己拆掉的那些**：早就悬空、指着空气的旧记录（别的工具或者手改留下的）不在这条路径里，
fixer 不会主动去全图清理 `poi/`（那属于 merge 的活，见第 2 节）。

**顺序永远是 merge → fixer：fixer 改过的地别再跑 merge。** merge 只管"`now` 和板子不一样就搬过来"，
它不知道哪边对：fixer 刚拆掉/换成水的方块（水草、悬空藤蔓、霜冰…），在 `now` 里还是原样，
再跑一趟 merge 就**原样搬回来**（实测：拿修过的板子再 merge 一个区域，搬回 28243 处，
全是 fixer 拆掉的水草一类）。要重跑就从头来：重新生成板子 → merge → fixer。

## 5. 规则插件（rules.so）

fixer 自己不判"这个方块合不合法"，它 `dlopen` 装 `rules.so`，逐格问插件。装的位置固定：
先找 **fixer 自己那个目录下的 `rules.so`**，没有再找当前目录下的 `rules.so`。

- 当前规则版本是 **26.1**（`rules.so.26.1`，`rules.so` 是指向它的符号链接）；
  插件在启动时自报版本，fixer 会打一行 `规则插件 …（版本26.1，22条规则、5个规则家族）`。
- 换一套规则：把 `rules.so` 指向别的 .so 即可（`ln -sf rules.so.26.2 rules.so`），fixer 不用重编。
- 自己写插件：接口在 `rules.hpp`（`Rules_Api` + `Blk_Info` + `Rules_Ctx`），必须导出
  `extern "C" const Rules_Api *rules_Entry(uint32_t abi,uint32_t size)`。
  `abi`/`size` 两边对不上就返回 NULL，fixer 会直接报错不干（不会有"带病跑"这种事）。
- **两边必须用同一套编译器/标准库**（这里是 g++ + libstdc++），因为 `Blk_Info` 里有 `std::string_view`。
- 插件合约（写规则必须守住）：**只能把东西变少**——拆掉，或把撑不住的面从 `true` 改成 `false`；
  不许放方块、不许把 `false` 改成 `true`。`FX_SET` 也允许把方块整个换成"更小"的另一种
  （霜冰化成水就是这样，见第 4 节），但换过去的状态不能又是规则表要管的方块、也不能多出能撑东西的面。
  破坏了这条，fixer 可能转不完（证明见 `fixer.cpp` 文件头）。

规则覆盖范围（26.1）：wiki 上 26.1 里"需要判断合法性"的方块都在表里了，只读自己那 6 个面，
外加紫颂植株要读的"旁边那株的下面"（斜下方那一格），
拿不准的一律放过，26.2/26.3 才有的方块一条都不收。具体清单和依据见 `ReadMeDeveloper.md`。

有一条**很容易写错**的结构：大垂滴叶（`big_dripleaf`）是"若干根 `big_dripleaf_stem` 互相叠着、
**最上面顶一片叶子**"（wiki《Big Dripleaf》Usage 原文），骨粉也是"把叶子顶高一格、在下面补一根茎"。
所以**叶子下面是自己的茎是正常形态**，不是悬空——规则表里必须认这一条（26.1.1 真图实测：一张区域
2123 片叶子里有 1469 片是这种；漏了的代价是 fixer 把它们连茎一起拆掉）。

**兴趣点方块**（村民的工作站：讲台/堆肥桶/酿造台/炼药锅/砂轮……，还有蜂箱、磁石、传送门、床）
在表里都登记成"明确不管"：wiki 上这些方块**没有**"支撑块没了会掉"的依据（唯一会掉的是钟），
所以它们悬空也**不拆**——误拆一个工作站等于把村民的职业和认领记录一起弄没了。
`test/rules26.sh` 里有 21 条"悬空的工作站必须留着"的反例盯着这条。

## 6. nbtrw：库的 demo

```sh
./nbtrw nbt    [file.nbt]              # 读一个 .nbt（或 test/work/3.txt 这种区块）并打印成 snbt
./nbtrw nbtw   [file.nbt]              # 读→写回去→再读，确认编码/解析一致
./nbtrw dat    [level.dat]             # 读 level.dat（gzip 的 NBT）并打印
./nbtrw mca    <目录> <rx> <rz> [cx] [cz] [w]   # 读区域文件里的一个区块；w=顺便回写自测
./nbtrw chunk  [file.nbt] [x] [y] [z] [新方块名]  # 读单区块文件、取方块、可选塞一个方块再解析回来
./nbtrw level  <存档目录>               # 打开存档：DataVersion、布局、三个维度的区域目录、区块(0,0)在不在
```

不给文件参数时的默认值：区块类用 `test/work/3.txt`（测试素材，见第 8 节），`dat` 用
`test/data/level.dat`（仓库里带的样例存档）。

`level` 这个子命令最适合"先确认路径和存档结构对不对"——它只读，不改任何东西。

## 7. 存档结构：新布局 / 老布局

`level.dat` 是 gzip 压缩的 NBT，里面的 `Data.DataVersion` 决定维度目录在哪，**严格按它判，不按目录在不在猜**：

| DataVersion | 布局 | 主世界 / 下界 / 末地 |
|---|---|---|
| ≥ 4774（26.1 快照6 起） | 新 | `dimensions/minecraft/overworld/region/`、`.../the_nether/region/`、`.../the_end/region/` |
| < 4774 | 老 | `region/`、`DIM-1/region/`、`DIM1/region/` |

读不到 `level.dat`（不是存档目录、文件坏了）时，merge 和 fixer 都会**直接拒绝干活**并报错，
不会瞎猜一个目录去改。实测过的版本号：26.1 = 4786、26.1.1 = 4788、26.1 快照6 = 4774、1.20.1 = 3465。


```sh
cd nbtrw
sh test/run.sh     # 一键回归：造世界 → 存快照 → merge → fixer → 用python独立核对逐格结果
sh test/conv.sh    # 连锁/收敛：挂一串悬空藤蔓，看是不是一趟拆完、第二趟0改动
sh test/safe.sh    # 安全检查：ASan+UBSan 编译整套 + 坏数据用例 + valgrind（越界/野指针/泄露/fd泄露）
sh test/safe.sh asan   # 只跑 sanitizer 那一半
sh test/safe.sh vg     # 只跑 valgrind 那一半
```

`run.sh` 里除了方块，还有几轮专门核对 `poi/` 和 `entities/`（合成世界 + 真存档），单独跑：

```sh
python3 test/check_poi.py        # merge对POI/实体的处理（合成世界：test/mkpoi.cpp 摆的）
python3 test/check_poifix.py     # fixer拆掉POI方块后记录跟着删
python3 test/check_poibad.py     # 坏实体/坏POI数据：跳过坏的、别的照做
python3 test/check_poi_scan.py <世界目录> [rx0 rz0 rx1 rz1] [strict]
                                 # 【手动、只读、慢】扫一个真存档的 poi/，查记录和方块对不对得上
```

`check_poi_scan.py` 是**拿真数据检验那张硬编码的"方块→兴趣点类型"表**的工具（表里漏一个方块、或者类型对错了，
它就会报出来；当初就是靠反向对拍发现漏了 `fletching_table` 制箭台）。它不进 `run.sh`（纯 python 逐格扫，
全存档要几分钟），只读，一个字都不写。`strict` 表示把"区块里有兴趣点方块却没有记录"也当失败——
原版在没有被玩家加载过的区块里可能本来就没有记录，所以默认只列出来。

核对脚本（`test/check*.py`）用的是另一套自己写的 Python NBT 解析器，和 C++ 代码不共享逻辑，
所以它说"0 个该拆没拆、0 个误拆"是真的独立结论。`run.sh` 会用到仓库里的真存档（`now/ new/ old/`，
有新布局的 `dimensions/…/region/r.0.0.mca` 时自动多跑一轮真数据），测试地图随便改随便删。

**地图数据和测试素材都不进 git**：`nbtrw/new|now|old/` 和 `test/work/` 在 `.gitignore` 里挡着；
各版本的整图目录（`1.20.4/`、`1.21*/`、`26.1.1*/`、`server/`）只是**从没被 `git add` 过**——
别顺手 `git add -A`，要挡得另加规则。`test/work/` 里那两块素材有就跑对应的几轮，
没有就自动跳过并说明，不影响其它测试：

| 素材 | 放哪儿 | 干什么用的 |
|---|---|---|
| 一块真实区块（NBT） | `test/work/3.txt` | `test/mk.cpp` 拿它当模板造合成世界；没它就跳过 merge A/B、参数检查、level 自测、check.py |
| 一个真实区域文件 | `test/work/r.0.0.mca` | "1024 区块只动 4 个"那一轮；没它就跳过 |
| 真存档 `now/ new/ old/` | `nbtrw/` 下（仓库根那三个也一样） | 真数据逐位置核对（方块 + 实体 + 兴趣点）；没有就跳过 |
| 任意一个真存档 | 任意路径 | `python3 test/check_poi_scan.py <世界目录>` 只读扫它的 `poi/`，查记录和方块对不对 |
| 下载的 wiki 原文/调研笔记 | `test/work/wiki/` | 写/核对规则时查依据用，测试本身不需要 |

`test/pal.cpp`（列出世界上出现过哪些方块）和 `test/props.cpp`（列出每个方块有哪些属性）是**写规则用的工具**，

## 9. 常见报错

| 输出 | 意思 / 怎么办 |
|---|---|
| `读不到 level.dat（不是存档目录？），什么都没干` | 路径给错了，或者那个目录真没有 `level.dat` |
| `维度名 xxx 认不出来（只认 overworld/the_nether/the_end），改用主世界` | `dims` 拼错了；只认这三个名字（带不带 `minecraft:` 都行，认关键字） |
| `范围太大（… 要碰 N 个区域文件，上限 …），坐标是不是写错了？什么都没干` | 坐标多半多打了一个 0；上限是 2^22 个区域文件 |
| `y范围不对（…，只在 ±4096 以内），坐标是不是写错了？什么都没干` | y 分量多半多打了一个 0；世界最高也就是 y=2031 |
| `new_path 和 now_path 是同一个目录（…）：new 会被改写、now 只读，必须分开给` | merge 是一边读 now 一边写 new 的，同目录会把要升级的地图改坏；`old` 和 `new` 同目录也会拒 |
| `规则插件返回了不认识的动作N，按'不动'处理（插件和rules.hpp对不上？）` | `rules.so` 和 fixer 的接口对不上（两边版本混了），换回配套的那一份 |
| `警告：… 在这N个区块里一个都没读到` | now 的区域目录不对（布局认错了/世界是空的） |
| `有失败（改不动…、存盘失败…、路径不对…）` | 看同一行上面的统计；退出码 255 |
| `nbt bad:overrun/root/tag（…）` / `chunk bad:inflate/compression type（…）` | 那个区块的数据坏了。**只跳过它自己**：这一块按"读不出来"处理、原样不动，整趟继续跑；坏了几次都计数，最多打前 10 条详情 |
| `entity bad:Position != slot / no DataVersion / no/bad Entities（chunk …）` | 那个**实体区块**形状不对（槽位和 `Position` 对不上、没版本号、`Entities` 不是列表）：整块跳过，`new` 那边一个字不动 |
| `poi bad:record not compound / record fields（…）` | `poi/` 里有一条记录形状不对（缺 `pos`/`type`/`free_tickets`，或者类型不对）：**这一条**丢掉，同一区块别的记录照做 |
| `有坏数据（NBT坏 x、压缩坏 y、实体区块 z、POI区块/记录坏 w 处），另有 N 个POI区块形状不对…` | 上面那些坏数据的汇总（merge 每个维度打一份，fixer 打一份）。坏的那些一个字没动，所以退出码是 255；`另有 N 个POI区块形状不对` 指 `Sections`/`Records` 不是该有的类型——那种**整块跳过**（不敢当成"这块没记录"，那会把里面的记录默默丢掉） |
| `有 N 条记录的票数超过该类型的上限（数据本来就不对，照抄没改…）` | `free_tickets` 比这个类型的上限还大（钟 32、村民用的 1、传送门这种 0）。**只提醒，不改数据**——票是认领状态的镜像，改了就是假数据；也可能是我们表里把类型对错了，看到就人工看一眼 |
| `merge: 注意 <文件>：表头一格区块都没有，但文件里还有 N 字节数据，没敢删` | 那个 `entities/`、`poi/` 区域文件的表头是空的、但后面还有数据。清理空文件时**只删 0 字节和正好 8KB 的**，这种留着不动 |
| `mca: 路径太长装不下（…）` | 存档路径长到拼不下文件名了：这时按"这个文件读不出来"处理，**不会**用截断出来的名字去读写/删别的文件 |
| `fixer: POI区块(x,z)写不回区域镜像` | 内存里改好的兴趣点区块写不回去（区域文件写失败），这一趟算失败（退出码非 255 之外的效果是 `err_cnt`），存档没被改坏 |
| `有 N 个区块的数据坏了（…），按"读不出来"跳过了，这些区块没动` | 上面那些坏数据的汇总（merge/fixer 各打一份）。这些区块没改，所以退出码是 255；想修就先备份、把坏区块挑出来 |
| `level: cache_id=…太大` | 程序内部参数写错了（不该出现），会当"读不出来"处理 |
| `chunk bad: 区域文件 <文件> 存在但读不出来（权限/IO错误/不是普通文件？）：这个区域一个字节都不会动` | 文件在、但读不出来。这时**不会**把它当"这里没有区块"去覆盖（那会把没读到的区块整片抹掉），也不写不删；退出码非 0 |
| `chunk bad: 区域文件 <文件> 只有 N 字节（不足8KB表头）…` | 区域文件被截断了：同上，一个字节都不动。0 字节的文件不算坏（游戏自己会留），merge 会正常当空文件写/删 |
| `level: 区域文件 r.x.z（维度d）读不出来，拒绝写它` | 同上，落盘那一步的拒绝。看文件权限/磁盘/是不是被别的程序占着 |
| `merge: 区域文件 <文件> 读不出来，不写也不删（免得把没读到的区块抹掉）` | 实体/POI 区域文件读不出来时的同一道保护 |
| `有 N 个区块的xPos/zPos和文件位置对不上，整块跳过了` | 存档有毛病（区块记的坐标和它所在的槽位不一致）。方块按文件位置读写、方块实体按 xPos 找，两套坐标会打架，所以整块不动；退出码非 0 |
| `有 N 个区块里出现了两段Y相同的section，整块跳过了` | 坏数据。初扫按"段"判、写回按 `find_Section`（只认第一个 Y 匹配的段），会"判A写B"删错方块，所以整块不动；退出码非 0 |
| `有 N 段读不出调色板（direct/>256条，本程序有意不读）、M 个位置的数据缺/短（坏数据）` | 前者是有意不读（留着不动，只报数）；后者是坏数据，退出码非 0 |
| `fixer: POI区域文件 r.x.z 读不出来，这个区域里拆掉的POI方块没能删记录` | 方块拆了、`poi/` 里那条记录删不掉（那是个指向空气的索引）。文件一个字节没动，退出码非 0 |
| `fixer: POI空文件删不掉 <文件>（…）` | 删不掉（权限/只读）。以前是静默的，现在报出来并让退出码非 0 |
| `merge: [维度] 跳过 N 个区块（一个方块都没搬）：now那边 mca不存在 a、表里没这个区块 b、数据读不出来 c、Status不是full d、没有Status字段 e、full但一个方块都没有 f、xPos/zPos对不上 g；new里没这个区块 h（不新建）、new那边读不出来 i；old里一个都没有 j` | 正常输出（不是失败）：这些格子一个方块都没搬，`new` 保留自己的地形。分类含义见第 2 节"跳过"那张表；其中 `数据读不出来`/`xPos/zPos对不上` 两类会让退出码非 0 |
| `merge: [维度] 跳过的位置把 new 那份的 InhabitedTime 清成 0（这趟清了 N 格…）` | 正常输出：跳过的地方按规矩把"被住过多久"清 0（只写本来不是 0 的）。`old` 给空串的那趟不清（那趟什么都不改） |
| `merge: 有 N 个区块在now里是空的/没生成完，整块跳过（保留new的地形）：…` | 老版本的提示语（现在的输出见上面"跳过 N 个区块"那行）：`now` 里有 C2ME/生成中断留下的残块。**不是失败**：这些位置保留了 `new` 自己的地形，免得把新板戳出游戏永远不补的空洞。`now` 里这种块很多就用 `./prune` 删掉（第 3 节） |
| `prune: 删了 N 个区块（其中没生成完的…）` | 正常输出：这些格子现在等于"没生成"，进游戏或跑一次 `chunky start` 就会按种子重新生成 |
| `prune: [维度] r.x.z 有读不出来的文件（region坏1 …），这个区域一个字节没动` | 那个区域里有读不出来的文件（权限/IO/不是普通文件）：保守起见整个区域不碰，退出码非 0 |
| `prune: mode 只能是0/1/2/3，给的是 N` | 第 6 个参数（mode）写错了 |
| `merge: 没给old：这一趟只统计（方块/实体/POI/空文件清理/InhabitedTime 全都跳过），new 一个字节都没改` | 正常提示（`old_path` 给的是空串时打） |
| `规则插件返回了不认识的动作N，按'不动'处理（插件和rules.hpp对不上？）` | `rules.so` 和 fixer 的接口对不上（两边版本混了），换回配套的那一份 |
| `规则插件没装上` | `rules.so` 不在 fixer 旁边也不在当前目录，或者 ABI 对不上（两条都会打原因） |

**注意**：坏数据（区域文件/level.dat 被改坏、压缩数据坏了）的策略是**跳过 + 计数**：
坏区块只影响它自己（那一个区块原样不动），整趟 merge/fixer 会跑完，最后在报告里写清楚跳过了几个，
退出码非 0。绝不会拿着半截数据去改存档——读不出来的东西一律不动。
（写出去的数据里"本来就不该出现"的情况还保留 `exit(-1)`，比如字符串超过 0xFFFF 字节。）

如果整趟一个区块都没读到（不是坏，是路径/布局不对），会打"一个都没读到"的警告并返回 255：
那时候先看 `region_dir` 打得对不对、`level.dat` 里的 DataVersion 是不是和你以为的一样。

## 10. 它不做什么（宁可放过，不可破坏）

- 不处理"MC 自己会算"的：沙子/沙砾/铁砧这些掉落、珊瑚缺水变死珊瑚、树叶腐烂、冰/霜冰融化、甘蔗旁边的水；
- 不处理"wiki 明说能悬空、或者根本没提支撑要求"的：活板门/栅栏门/花盆/铁链/末地烛/床/避雷针
  （避雷针 wiki 全页没写支撑，按"没写就当不用支撑"放过；脚手架**是**判的——它要下面有支撑或旁边也是脚手架）；
- 不拆**兴趣点方块**（村民工作站/炼药锅/蜂箱/磁石/讲台…）：wiki 上它们没有"支撑没了会掉"的依据，
  悬空也留着（拆了会连带删掉 POI 记录，村民就丢了职业/认领；`rules26.sh` 里有专门的反例）；
- 不处理"6 个面判不出来"的：下界传送门（要整个门框）、蘑菇方块（那 6 个面是贴图不是合法性）；
- 不算光照、不算高度图：merge 会把 `isLightOn`/`Heightmaps` 删掉让 MC 自己重建；**fixer 不删**，
  它拆的多是草/藤蔓/雪这类不挡光的小方块，游戏下次加载/方块更新会自己把光照和高度图修正回来
  （这一点是已知差别：要绝对干净，就在 fixer 之后再让游戏重算，或者拿 merge 的 new 当输出）；
- 不支持 >256 条的 direct 调色板（遇到就"这一格读不出来"，留着不动）；
- **兴趣点不凭方块新造记录**：merge 会把"方块对不上"的记录删掉、把 `now` 里已有的记录照搬过去
  （报告里的"补 N 条"就是这种照搬），但**不会**给"有床/工作站却没有记录"的位置凭空补一条
  （那是游戏加载区块时自己该干的）——所以合并完可能出现"方块在、索引里没有"的位置，游戏下次加载会补上；
- **兴趣点的票数原样照抄**（不夹到上限、不重算）：票是"实体那边还剩几张"的镜像，改了就成了假数据；
- **不动形状坏的兴趣点区块**：`Sections`/`Records` 类型不对的**整块跳过**并计数（退出码非 0），
  宁可留着旧数据让人去看，也不当成"这块没记录"去覆盖（报告里那句"N 个 POI 区块形状不对"实际是
  "读不出来 / 形状不对 / 写不进去"合计的，要看详情翻上面的坏数据行）；
- **不碰 `now` 和 `old`**：merge 只写 `new`（`entities/`、`poi/` 的空文件清理也只清 `new` 的目录）；
- **不读写不出来的区域文件**：文件存在但读不出来（权限/IO/截断）时，既不写也不删，报出来 + 退出码非 0；
  宁可这一趟白跑，也不拿"没读到的东西"去覆盖（那会静默抹掉整片区块）；
- **不给 `xPos`/`zPos` 对不上的区块做任何改动**（方块/实体/兴趣点全跳），因为方块实体的坐标是从
  区块自己的 `xPos` 算的，两套坐标一打架就会在错的位置搬/删实体。

- **不迁移 `level.dat` 的内容**：merge 只读 `new` 的 `DataVersion`（决定维度文件在哪），
  种子/出生点/时间/天气/`gamerules`/龙战状态/`Player` 都留在 `now` 那份里，
  `playerdata/`、`scoreboard.dat`、`advancements/`、`stats/` 也一个都不搬——
  要保留玩家数据的话得自己拷（`DataVersion` 必须留新板的，不能拿旧的覆盖）；
- **不管"合并之后又跑了一次 merge"**：fixer 拆掉的方块在 `now` 里还是原样，再跑一次 merge 会被当成
  "玩家的改动"搬回来。代码里没有防护（没有标记文件），靠的是**约定**：`merge → fixer` 只走一趟；
  中间要重跑，就把 `new` 恢复成没合并过的裸图（或者用 `old=""` 的只统计模式看看）。

拿不准的都不动：**宁可漏拆，不乱拆玩家搭的东西。**
